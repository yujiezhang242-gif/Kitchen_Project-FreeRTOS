# 系统设计与实施路线

> 本文件保留最初评估和演进目标。当前已实现分通道控制、DHT 边沿解码、通信/存储服务和六任务固件代码，状态以 README、功能与通信协议、验证记录为准。下文“尚未实现”属于初始设计时点。

## 1. 基于源代码的评估

评估依据为原项目 C 源码、FreeRTOSConfig.h 和 Keil 工程配置。目录中的简历、面试材料和 Word 文档未作为功能需求或操作指令。

| 位置 | 现状与影响 | 修改方向 |
|---|---|---|
| usr/main.c 的 EXTI ISR | 延时 10ms、绘屏，调用非 FromISR 的挂起/恢复接口 | ISR 只清标志与投递通知，任务消抖和生成按键事件 |
| bsp/EXTI/exti.c | IRQ 数值优先级 2；当前内核允许调用系统 API 的边界为 3 | 使用 RTOS API 的 IRQ 必须按配置设置合法数值优先级，建议统一为 5 并保留分组 4 |
| 多个任务及 ISR | 同时写 LCD，共享底层 SPI 和显示状态 | 只有 UI 任务操作 LCD；其他任务发送状态副本 |
| main.c 控制 | 信号量、共享 biao/flag 与挂起任务混合 | 控制任务独占状态，以事件和回差表达行为 |
| 光照队列 | 长度 1，生产者无限等待；消费者被挂起后可能阻塞采集 | 状态使用覆盖邮箱；命令使用有界队列，统计丢弃 |
| DHT11 | 返回值未检查；接收缓存为全局，未响应可能沿用旧数据并通过校验 | 每次清理局部帧、逐阶段超时、明确错误码，成功才更新时间戳 |
| ADC | 轮询 EOC 无超时；电阻计算保存到 u16 可能截断 | 驱动添加超时；用足够宽整数或直接标定 ADC；后续改 DMA |
| TIM3 PWM | 没有明确设置 TIM_OCInitStructure.TIM_Pulse | 初始化确定占空比和启动状态；示波器确认周期与脉宽 |
| FreeRTOS 配置 | V9.0.0，10KB heap；断言仅 printf 后继续；未启用栈/分配失败钩子 | 断言进入可诊断故障路径，开启监测，审计所有创建返回值 |
| 系统启动 | 创建对象未判空，在临界区内创建并删除启动任务 | 调度器启动前创建对象和任务，失败时保持已定义的输出状态 |
| 按键初始化 | main 未调用 KEY_Init，需核查 GPIO 是否由其他代码初始化 | 显式初始化，验证电平和上下拉 |

原 delay_ms 在调度器运行后会调用 vTaskDelay，因此不能简单认定所有 delay_ms 都是忙等待；应逐个检查调用上下文。delay_us 是轮询，DHT 微秒时序仍会受到抢占影响。

## 2. 分层与所有权

依赖方向：App → Services → Drivers → BSP。业务规则不直接包含 STM32 头文件。

- BSP：时钟、引脚、NVIC、DMA 映射、复位原因，统一板级资源表。
- Drivers：ADC、温湿度、LCD、UART、Flash、PWM，返回成功/超时/硬件错误。
- Services：传感器质量处理、消息路由、帧解析、参数存储、日志、健康监控。
- App：控制状态机、UI 页面、命令处理与远程状态映射。

每个资源只有一个写入者。Control 写业务状态，UI 写 LCD，Comm 写 UART TX，Storage 写非易失存储。日志通过有界队列进入存储任务，不能在任意任务里直接刷 Flash。读者拿消息副本，不能持有生产者正在更新的结构体指针。

## 3. FreeRTOS 任务设计

下表为初始设计预算，需要板上测量后调整；栈单位是 Cortex-M3 的 32 位字，不是字节。

| 任务 | 优先级 | 触发/周期 | 初始栈 | 主要职责 |
|---|---:|---|---:|---|
| Health | 5 | 500ms | 192 | 检查心跳、堆和栈余量，满足条件才喂 IWDG |
| Control | 4 | 事件唤醒，最长等 100ms | 256 | 输入校验、联动决策、命令仲裁、告警 |
| Sensor | 3 | ADC 100ms、温湿度 2s | 256 | 采集、滤波、错误码、时间戳 |
| Comm | 3 | DMA/接收通知，带超时 | 384 | 收发、帧解析、应答、连接状态机 |
| UI/Input | 2 | 20ms 按键；200ms 显示 | 384 | 稳定电平消抖、按键事件、局部刷新 |
| Storage | 1 | 队列唤醒 | 256 | 合并保存参数、日志和磨损管理 |

六个任务用户栈合计约 6.75KB，未包含 TCB、idle/timer 栈、队列、内核堆管理开销、C 库及全局区。原配置 heap=10KB 不能直接假定足够。必须查看 map、最小剩余堆、每个任务栈水位；不要盲目增大 heap 占满 RAM。若使用软件定时器，回调只发事件，不做 I/O；其优先级应有明确设计。

Control 不能仅等待传感器消息，否则断线后没有新消息就无法检测超时。每次唤醒重新计算剩余定时，超时也调用 kitchen_step。周期采集用 vTaskDelayUntil 避免累计漂移。

### 消息与背压

- Sensor → Control：长度 1 的快照邮箱，用 xQueueOverwrite；包括数值、各通道有效位、采样时间、序号。当前核心为简化整体 valid，集成版应拆分通道有效性，避免单一传感器故障影响全部功能。
- UI/Comm → Control：命令队列长度初始 8，包含 source、request_id、command、value。发送失败立即 BUSY，不永久阻塞。
- Control → UI、Control → Comm：分别设置独立状态邮箱。多个消费者不能共用一个队列获取广播。
- 各任务 → Storage：日志队列初始 16，满时累加 dropped_count，关键故障另留固定槽；避免每周期无变化写日志。
- UART/DMA ISR → Comm：使用 FromISR 通知或队列，并按 xHigherPriorityTaskWoken 请求切换；不得用任务上下文接口。

任务启动后才使能会访问 RTOS 对象的中断。ISR 不做 printf、屏幕刷新、阻塞等待或业务判断。当前 core 输入时间单位为毫秒，适配层统一转换，不得把不同 tick 频率的值直接当毫秒；回绕周期也必须一致。

## 4. 业务功能与状态机

已实现：温度/湿度/光照回差；超时或无效数据告警；消音计时；新告警源打断消音；故障恢复；演示通风请求。core 不负责 PWM、传感器和消息队列。

后续实现：

1. AUTO/MANUAL/FAULT 模式。手动命令带有效期，到期回到自动。明确优先级：故障处理 > 有效手动覆盖 > 自动规则。告警确认只改变声音，不清除故障。
2. 高温、温湿度离线、ADC 越界、执行器无响应分别生成错误码；无反馈硬件时只能报告“已下发”，不能报告“已到位”。
3. UI 首页显示数值、数据年龄、模式、输出和网络状态；另设阈值设置、告警记录、系统诊断页。
4. 参数提交先校验阈值关系和范围，再统一替换运行配置；保存成功前标记“未保存”。避免重启才能验证错误。
5. 光照当前只是 ADC 原始值，未经标定不要显示 lux。DHT 分辨率不能由显示小数凭空提高。

系统状态 BOOT → SELF_TEST → RUN；可恢复故障进入 DEGRADED，影响任务和输出的严重故障进入 FAULT。启动自检覆盖配置、传感器、显示和通信可用性；每项有时限。

## 5. 驱动升级

ADC：先补齐轮询超时；再做定时触发 + DMA 循环缓冲，用半满/全满事件交接已完成的数据块。写明缓冲区寿命和处理截止时间，超时计 overruns；不让消费者读 DMA 正在覆盖的半区。

温湿度：第一阶段保留 DHT11，但明确帧超时与校验，失败不沿用旧帧。禁止通过长时间全局关中断保时序。若抢占下不能可靠读取，换适合现有总线的传感器，或重写为定时器捕获方案，并先检查引脚资源。

UART：DMA 接收配合空闲事件，按写指针增量搬运到软件环形缓冲。空闲不是协议帧边界；处理 DMA 回绕、满缓冲与 UART ORE。发送由单任务管理 DMA，直到完成才能复用缓冲区。

PWM：统一角度/脉宽转换、限幅、上电位置和失败位置；用示波器验证。机械限位和舵机供电要实测，不能只依据现有 CCR 数字推断角度。

## 6. 通信和远程版

先实现串口协议，让脚本可以验证全部命令；之后把同一命令模型接到联网模块。现有代码只有 printf 温湿度，没有看到完整的 MQTT、AT 状态机或远程命令通道，不能算已联网。

建议自定义调试帧：SOF(0xAA55，2B) | version(1B) | type(1B) | seq(2B) | length(2B) | payload(0..128B) | crc(2B)。多字节字段统一小端；CRC-16/MODBUS，初值 0xFFFF，多项式反射 0xA001，覆盖 version 至 payload，低字节先发。该帧只是本项目协议，不等同 Modbus RTU。

解析器按字节流推进：搜头、读固定头、校验长度、收载荷与 CRC、校验、派发。长度超限立即拒绝，半包超时恢复搜头，坏帧后重新同步。命令含 READ_STATUS、SET_THRESHOLDS、SET_MODE、ACTUATOR_REQUEST、ACK_ALARM、READ_DIAG、SAVE_CONFIG。应答保留 seq，状态包括 OK、BAD_LENGTH、BAD_VALUE、BUSY、UNSUPPORTED。

远程状态机：OFFLINE → INIT → CONNECTING → ONLINE → BACKOFF。每阶段有超时、重试上限和可取消机制；网络故障不得阻塞 Control。指数退避设置上限并加入抖动。发布数据带设备标识、序号、数据年龄和有效性。

下行命令必须走 Control，不能由网络任务直接改 GPIO。使用 request_id 做幂等，重复请求返回已有结果；具有动作副作用的旧指令不在重连后无限重放。远程访问的认证、凭据保存及加密能力应依据实际模块确定；CRC 只检错，不提供认证。

## 7. 存储与日志

参数格式显式序列化：magic、schema_version、generation、payload_length、payload、CRC、commit 标记。不要直接把带填充的 C struct 写入 Flash。

采用两个独立擦除单元 A/B：保留旧有效记录 → 擦除非活动单元 → 写头与内容 → 校验回读 → 最后提交标记。启动仅接受已提交且 CRC 正确的记录，选择较新的代数；都无效则加载默认值并记录原因。代数比较需处理回绕。参数写入合并、限频，不能每秒擦写。

内部 Flash 擦写可能影响运行时延，需要实测阻塞和中断延迟，安排维护窗口；不能因为放进低优先级任务就认为没有影响。链接脚本必须排除配置区域；若升级加入 Bootloader，重新统一分区，不能让存储覆盖固件。

日志采用有限容量循环记录：启动/复位原因、故障产生与恢复、参数修改、连接状态、队列溢出。先用 RAM 环形日志和串口导出，再按容量决定外部存储；不默认加入文件系统。

## 8. 健康监控

每个任务只在完成一次有意义的工作或有效检查后更新心跳。等待命令的任务也要有有界等待并上报存活。Health 根据每个任务自己的截止时间判断，而非要求同时清零一个共享位图。核心任务超时不继续喂狗，保存最小诊断线索，待看门狗复位。

开启栈溢出与 malloc 失败钩子；故障钩子中避免动态分配和复杂 printf。记录任务标识、错误码和复位原因。HardFault 捕获堆栈寄存器需要单独、经验证的异常入口，不能在此声称已实现。

## 9. 升级的准入条件

升级是独立里程碑，不作为第一版承诺。先量化固件和 Bootloader 大小、参数区、镜像暂存容量、擦写时延和启动校验耗时。64KB Flash 下不要直接承诺内部双镜像。

若采用外部暂存：下载分块、长度边界、完整镜像校验、版本信息和断点记录；Bootloader 可重新执行安装，所有掉电阶段有恢复路径，部分镜像不能启动。CRC 不能验证发布者身份；如要求可信升级需设计签名验证及密钥策略。没有验证掉电恢复前不宣称 OTA 完成。

## 10. 分阶段实施与验收

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| P0 当前完成 | 源码审计、架构、控制核心、主机测试 | make test 通过；未宣称板级集成 |
| P1 本地重构 | 新 main、任务和消息、驱动错误处理、UI 独占、按键消抖 | 拔掉传感器有故障提示；高低阈值回差正确；ISR 无阻塞和非法 API |
| P2 工程化 | UART DMA、帧解析、配置 A/B、日志、诊断、IWDG | 半包/坏包/洪泛可恢复；参数断电可恢复；任务卡死触发复位 |
| P3 远程版 | 模块状态机、遥测、下行、重连与去重 | 断网后本地持续运行；重复命令不重复动作；重连状态一致 |
| P4 升级版 | 分区、Bootloader、镜像验证、恢复 | 各擦写阶段断电均能恢复到完整可启动镜像或恢复模式 |

建议验收目标，均待实测：Control 周期不超过 100ms；按键有效事件延迟不超过 100ms；数据超过设定寿命后最多再等一个控制周期进入故障；连续运行 24 小时无异常复位和持续堆下降。记录最大响应时间而不只看平均值。

测试矩阵：阈值上下边界、消音到期、新故障、传感器断线/错误校验、ADC 超时、队列满、串口随机流和突发流、配置破坏、写入中掉电、网络断开、任务故意卡死、计时回绕。保存固件版本、测试输入、预期和实际结果。

## 11. 下一步落地顺序

先复制原工程到明确的固件工作目录并建立版本基线；保留原有版权说明。把 core 加入 Keil 工程，替换 main 的共享标志与任务挂起逻辑。用实测板级表确认 LCD/SPI、UART、TIM、ADC、按键、DHT 引脚没有冲突，再实现 P1。每阶段能独立编译、烧录和验收后再增加下一阶段。

当前尚需确认：实物 MCU 型号和板卡、传感器及舵机型号、LCD 接口、Wi-Fi 模块及固件、是否允许加外部存储/换板、Keil 编译环境是否可用。这些信息决定引脚、驱动和容量方案，不影响当前控制核心与架构设计。
